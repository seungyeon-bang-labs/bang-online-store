# BANG Online Store

남성 패션 쇼핑몰의 상품 탐색부터 주문 후 관리까지의 사용자 경험을 구현하는 개인 포트폴리오 프로젝트입니다.

상품 옵션·재고·할인, 장바구니, 주문, 쿠폰, 회원 등급, 리뷰, 교환·반품처럼 쇼핑몰에서 자주 만나는 업무 흐름을 화면과 도메인 로직으로 나누어 설계하는 데 초점을 맞췄습니다.

> 현재 Supabase Auth 기반 회원 인증과 상품·카테고리·상품 집계·할인·홈 진열의 실제 DB 조회, 회원 장바구니 RPC 연결을 구현했습니다. 장바구니 스키마 적용·로컬 검증을 마쳤고, 단순화한 장바구니 클라이언트로 승인된 데모 계정의 변경·실패 복구·비회원 장바구니·로그인 병합을 실제 브라우저에서 검증했습니다. 물리적 다중 기기 확인은 후속 검증입니다. 상품 이미지는 Supabase Storage에서 제공합니다.
>
> 기존 주문·리뷰·문의·혜택과 이벤트 배너 등 데모 내역은 fixture를 유지하며 단계적으로 DB로 전환하고 있습니다. 실제 결제와 주문·재고의 DB 트랜잭션은 구현 범위에 포함되지 않습니다.

## 프로젝트 목표

- Next.js App Router로 반응형 쇼핑 경험을 구현한다.
- 주문·혜택·반품 업무를 도메인 단위로 분리한다.
- fixture로 사용자 흐름을 검증하고, Repository를 통해 실제 데이터 소스로 점진적으로 전환한다.
- 모바일과 데스크톱에서 일관된 탐색·구매·마이페이지 경험을 제공한다.

## 구현 범위

### 상품 탐색과 구매 흐름

- 메인 상품 슬라이더, 신상품·세일·베스트 상품
- 카테고리 및 세부 카테고리 탐색
- 상품 상세, 색상·사이즈 옵션, 재고·품절 상태, 수량 선택
- 장바구니 추가, 옵션 변경, 선택 상품 관리
- 신규 주문은 DB 전환 전까지 준비 중으로 안내하며, 서버 액션에서도 생성을 차단
- 검색 오버레이와 인기·최근 검색어 UI

### 회원 인증

- 이메일·비밀번호 로그인 및 로그아웃
- 회원가입과 이메일 OTP 인증
- 미인증 사용자의 이메일 인증 재개
- 인증번호 기반 비밀번호 재설정
- 회원 상태에 따른 보호 페이지 접근 제어
- 서버 환경변수에 따른 배포 데모 인증 기능 제한

### 마이페이지와 데모 내역

- 실제 로그인 회원의 이름과 회원 정보 조회
- 기존 데모 주문 목록·상세·영수증, 주문 취소와 교환·반품 요청
- 배송지, 쿠폰, 포인트, 회원 등급, 최근 본 상품, 위시리스트
- 리뷰 작성·수정·삭제 및 1:1 문의 관리

쇼핑몰 내역의 DB 영속화는 후속 작업입니다. 실제 회원 정보와 기존 쇼핑몰 데모 내역의 데이터 출처를 구분해 사용합니다.

### 기타

- 이벤트 목록·상세와 혜택 UI
- 고객센터, 공지, FAQ, 교환·반품 안내
- 스냅샷 피드와 업로드 화면

## 아키텍처

프로젝트는 App Router 위에 feature, domain, shared 계층을 둔 모듈러 모놀리스 구조입니다.

```text
src/
├─ app/       URL, 페이지, 레이아웃, API Route, Server Action
├─ features/  화면 기능과 사용자 상호작용
├─ domains/   업무 데이터, 규칙, 조회·변환 로직
└─ shared/    공통 UI, 레이아웃, 유틸리티, 타입
```

```text
app → features → domains → shared
app → domains
features → shared
```

- `app`: `(storefront)`, `(auth)`, `(mypage)` Route Group으로 화면 맥락을 분리합니다. 검색과 카테고리는 Parallel Route와 Intercepting Route로 오버레이를 제공합니다.
- `features`: 상품, 장바구니, 인증, 이벤트, 마이페이지처럼 사용자에게 보이는 기능 단위 UI를 관리합니다.
- `domains`: 상품·주문·회원·혜택 등 업무 개념별 DTO, Repository, Service, Mapper, ViewModel과 입력 검증 스키마를 관리합니다.
- `shared`: 공통 UI, 사이트 레이아웃, 포맷터, 경로 유틸리티, 공통 타입을 관리합니다.

Repository는 데이터 조회와 관계 조립을, Service는 업무 흐름을, Mapper는 DTO·Model·ViewModel 사이의 변환을 담당합니다. 인증처럼 서버에서만 실행할 코드는 클라이언트가 사용하는 순수 함수·타입과 구분합니다.

## 데이터 전략과 현재 상태

| 영역 | 현재 데이터 출처 |
| --- | --- |
| 회원·약관 | Supabase DB |
| 로그인·회원가입·이메일 인증·비밀번호 재설정 | Supabase Auth |
| 상품·스타일·색상·옵션·카테고리 | Supabase DB |
| 상품·카테고리 이미지 | Supabase Storage |
| 현재 카탈로그의 상품 집계·할인·홈 진열 설정 | Supabase DB |
| 기존 주문·리뷰·문의·혜택·마이페이지 데모 내역 | Fixture |
| 비회원 장바구니 항목·로그인 병합 요청 ID | 브라우저 localStorage(`bang-cart:v2`) |
| 회원 장바구니 항목·처리 이력 | 실제 세션을 확인하는 Supabase RPC·DB |
| 장바구니 화면 캐시·선택 상태 | Provider별 Zustand 메모리 상태 |
| 장바구니 상품의 가격·재고·옵션 조회 | Supabase DB |

루트 CartProvider가 서버가 알려 준 접근 상태로 장바구니를 시작하며, 계정이 바뀐 서버 화면이 오면 장바구니 상태를 새로 만들어 이전 계정의 장바구니가 섞이지 않습니다. 장바구니가 다른 계정을 먼저 알게 되면(`access_changed`, 비회원 진입 때 발견한 로그인) 직접 바꾸지 않고 서버에 화면을 다시 요청해 헤더·마이페이지와 같은 계정으로 맞춥니다. 장바구니 통신은 Server Action이 아닌 Route Handler(`/api/cart/access`, `/api/cart/read`, `/api/cart/operations`)와 fetch로 처리해 라우터 화면 갱신과 분리하며, 로그인·OTP 성공은 서버 redirect로 끝납니다.

장바구니 요청은 한 번에 하나만 보내고, 변경은 누르는 즉시 화면과 헤더 개수에 반영합니다. 응답이 실패하거나 형식이 맞지 않거나 15초 안에 오지 않으면 서버 장바구니를 다시 읽어 맞추고, 다시 읽기도 실패하면 마지막 서버 장바구니로 되돌린 뒤 `다시 시도`를 보여줍니다. 비회원 변경은 localStorage의 최신 항목에 바로 저장한 뒤 상품 정보를 받아 화면을 맞춥니다. 로그인하면 비회원 항목을 한 번에 옮기며, 같은 요청 ID를 다시 보내도 서버가 한 번만 처리합니다. 응답을 받지 못한 병합은 다음 시작 때 같은 ID로 다시 보냅니다. 다만 병합하는 동안 다른 탭에서 비회원 장바구니를 바꾸면 요청 ID가 새로 정해져, 드물게 수량이 한 번 더 담길 수 있습니다.

다른 탭의 변경과 로그인·로그아웃은 장바구니 화면에 들어가거나 새로고침할 때 반영합니다. 다른 계정으로 바뀐 뒤 이전 화면에서 변경하면 서버가 `access_changed`로 막고 화면을 새 계정으로 다시 받으므로 이전 계정에는 저장되지 않습니다. 탭 간 실시간 동기화는 하지 않으며, 로그인 병합 외에 응답을 모르는 요청은 저장하거나 다시 보내지 않습니다. 비회원 장바구니는 탭마다 localStorage를 읽고 바로 덮어쓰므로, 두 탭에서 거의 동시에 담거나 바꾸면 드물게 한쪽 변경이 저장되지 않을 수 있습니다. 병합 응답을 받지 못한 채 로그아웃하고 다른 계정으로 로그인하면, 남아 있는 비회원 항목이 그 계정에도 병합될 수 있습니다.

선택은 장바구니 진입 시 전체 미선택이며 저장하지 않습니다. 현재 재고가 0인 항목은 수량을 보존하되 선택·증감을 제한합니다. 회원의 품절 옵션 새 담기는 서버가 막고, 비회원이 담은 품절 옵션은 선택할 수 없는 줄로 보이며 로그인 병합 후에도 같은 품절 줄로 남습니다. 재고 예약·차감과 Realtime·주기적 조회는 포함하지 않으며 진입·변경·재시도 등 지원하는 재조회 시점에 가격·재고를 갱신합니다.

실제 카탈로그 조회와 기존 데모 내역 조회는 의존성을 구성할 때 명시적으로 구분합니다. DB 조회 실패 시 fixture로 자동 대체하지 않습니다.

신규 주문은 상품과 주문 조회의 데이터 소스가 다른 전환 중간 상태이므로 생성을 제한합니다. 주문 DB 전환 시 생성·조회 소스를 연결하고, DB 전용 신규 상품의 주문 목록·상세 조회와 판매 중지 후 과거 주문 표시를 검증합니다.

상품·카테고리와 상품 집계·할인·홈 진열을 DB에 연결했습니다. 판매량은 고정 데모 값으로 자동 집계·초기화하지 않습니다. 현재 할인 기간은 서울 기준 2026-10-19 00:00부터 2027-10-19 00:00 미만이며, 서버 재조회 때 유효한 할인 하나를 선택합니다. 이미 열린 화면의 가격을 종료 시각에 즉시 갱신하는 기능은 포함하지 않습니다. 기존 데모 내역용 상품은 고정 판매량·할인을 별도 출처로 유지합니다.

상품·카테고리 이전에 사용한 일회성 스크립트는 정리했으며, 적용·검증 기록과 DB SQL은 [Supabase 문서](./supabase/README.md)에 남겨 두었습니다. 집계·할인·홈 진열 초기 등록 SQL은 이미 적용한 변경 이력으로 보관하며 재실행하지 않습니다.

## 시작하기

### 요구 사항

- Node.js 24.12.0 (`.nvmrc` 참고)
- npm
- 프로젝트의 DB 구조·권한·Storage와 Auth 설정이 준비된 Supabase 프로젝트

### 설치 및 실행

```bash
nvm use
npm ci
cp .env.example .env.local
chmod 600 .env.local
```

`.env.local`에 아래 환경변수를 설정한 뒤 실행합니다. 현재 앱은 실제 DB를 조회하므로 환경변수 복사만으로는 실행 준비가 끝나지 않습니다.

```bash
npm run dev
```

개발 서버를 실행한 뒤 [http://localhost:3000](http://localhost:3000)에서 확인할 수 있습니다.

다른 Supabase 프로젝트를 사용한다면 DB 구조·권한·Storage를 준비하고 `next.config.ts`의 이미지 허용 호스트도 맞춰야 합니다. DB 적용 조건은 [Supabase 문서](./supabase/README.md)에서 확인합니다.

## 환경변수와 데모 모드

`.env.example`을 복사한 후 로컬 값만 `.env.local`에 입력합니다. `.env.local`과 실제 인증 정보는 커밋하지 않습니다.

| 변수 | 용도 | 설정 조건 |
| --- | --- | --- |
| `SUPABASE_URL` | Supabase 프로젝트 URL | 앱 실행 시 필수 |
| `SUPABASE_ANON_KEY` | 공개 조회·인증용 키 | 앱 실행 시 필수 |
| `PASSWORD_RECOVERY_SECRET` | 비밀번호 복구 임시 인증 쿠키 암호화 | 비밀번호 재설정 기능 사용 시 필요 |
| `AUTH_FEATURES_ENABLED` | 회원가입·이메일 인증·비밀번호 찾기 허용 여부 | 정확히 `true`일 때 허용, 기본값은 제한 |

`PASSWORD_RECOVERY_SECRET`은 무작위 32바이트를 Base64로 인코딩한 값을 사용합니다. 앱의 일반 환경변수에 관리자용 service-role 키를 사용하지 않습니다.

로컬에서 인증 기능을 검증하려면 `AUTH_FEATURES_ENABLED=true`로 설정합니다. 배포 데모에서는 `false`로 제한하며 로그인·로그아웃은 계속 사용할 수 있습니다. 제한 모드에서는 로그인 폼에 데모 계정이 미리 입력됩니다. 이 환경변수는 사이트 화면과 Server Action을 제어하며 Supabase 프로젝트 자체의 Auth 설정을 바꾸지 않습니다.

## 명령어와 검증

```bash
npm run dev                    # 개발 서버 실행
node --test tests/*.test.mjs    # Node 테스트 실행
npm run lint                   # ESLint 검사
npm run typecheck              # TypeScript 검사
npm run build                  # 프로덕션 빌드
npm run start                  # 빌드 결과 실행
```

일반 테스트는 실제 DB를 변경하지 않습니다. DB 통합 테스트는 별도로 준비한 격리 PostgreSQL 컨테이너에서만 실행하며, 해당 환경이 없으면 건너뜁니다. 실행 조건과 적용 기록은 [Supabase 문서](./supabase/README.md)에서 확인할 수 있습니다.

프로덕션 빌드에서 사용하는 Google Fonts를 다운로드할 수 있는 네트워크 환경이 필요합니다.
