# 회원가입 저장 트리거 적용 안내

2026-10-11 사용자 승인 후 Supabase 프로젝트 `plamqblmcavrtioajopz`에 마이그레이션을 적용했습니다.
트리거 두 개의 활성화, 함수 본문과 로컬 SQL의 일치, 기존 데이터·RLS·외래 키·RPC 권한 유지를 읽기 전용으로 검증했습니다. 기존 인증 계정 1개·회원 1개·약관 동의 3개는 그대로입니다.
실제 회원가입·이메일 발송·OTP 인증을 통한 종단 간 검증은 아직 진행하지 않았습니다. 아래 적용 순서는 새 환경에 적용할 때의 안내이며, 이미 적용한 DB에 마이그레이션을 다시 실행하지 않습니다.
이번 적용은 SQL Editor에서 실행했으며 Supabase CLI의 마이그레이션 이력에는 등록하지 않았습니다. 추후 `supabase db push`를 도입할 때 이 SQL을 재실행하지 않도록 이력부터 정리해야 합니다.

## 변경되는 흐름

1. 서버 액션이 이름·휴대폰·필수 동의와 화면에 표시된 약관 ID 목록을 검증합니다.
2. Auth 계정을 생성하는 트랜잭션에서 트리거가 회원과 약관 동의를 저장합니다. 저장 실패 시 Auth 계정 생성도 취소됩니다.
3. 이메일 OTP 인증 시 회원의 이메일 인증 시각만 갱신합니다.
4. 로그인·인증 후 서버 세션과 회원 상태를 확인합니다. 회원 조회 재시도에는 OTP를 다시 제출하지 않습니다.

DB 트랜잭션은 이메일 배달과 브라우저의 응답 수신까지 보장하지 않습니다. 통신 결과가 불명확하면 계정을 자동 삭제하지 않고 로그인 화면에서 인증을 이어갑니다.

## 적용 순서

- Supabase 프로젝트 `plamqblmcavrtioajopz`에서 `checks/signup-preflight.sql`을 읽기 전용으로 실행합니다.
- Auth와 회원의 누락·불일치가 없고, 예상하지 못한 Auth 트리거가 없으며, 활성 약관 코드에 중복이 없는지 확인합니다. 문제가 있으면 기존 데이터를 먼저 검토합니다.
- 실제 DB 변경에 대한 별도 승인을 받은 뒤 `migrations/20261011000000_atomic_signup.sql` 전체를 한 번 실행합니다. SQL 자체도 기존 데이터와 트리거를 검사하며 불일치 시 트랜잭션을 취소합니다.
- 새 앱 코드와 SQL을 함께 전환합니다. 이전 앱은 `displayed_term_ids`를 보내지 않으므로 새 트리거 적용 후에는 기존 가입 요청이 실패합니다.
- 승인된 테스트 계정으로 가입·이메일 인증·미인증 로그인 복구를 확인합니다. 계정 생성과 이메일 발송은 별도의 외부 변경입니다.

마이그레이션은 회원 테이블, 기존 데이터, RLS, 외래 키, 기존 `complete_signup` RPC를 유지합니다. 현재 회원가입·OTP 경로는 DB 트리거를 사용하며 해당 RPC를 호출하지 않습니다. 이전 가입 완료 함수와 전용 관리자 클라이언트, 관련 입력 스키마는 미사용 애플리케이션 코드로 정리했습니다. DB의 기존 RPC와 이를 반영한 생성 타입은 유지합니다.

## 적용 조건과 범위

- 이메일·비밀번호 가입과 이메일 OTP 인증을 대상으로 합니다. OTP는 앱 기준 6자리·300초입니다. Supabase Auth 설정도 같은 값이어야 합니다.
- 트리거는 모든 `auth.users` INSERT에 적용됩니다. 관리자 생성·초대·OAuth 등도 이름, 휴대폰, 약관 ID 메타데이터가 없으면 실패합니다. 다른 가입 경로를 추가할 때 함께 설계해야 합니다.
- 약관 버전 ID는 내용과 요구 조건이 바뀌면 새 ID로 발행해야 합니다. 현재 약관 목록과 화면의 목록이 달라지면 페이지를 새로고침하고 다시 동의해야 합니다.
- 확인된 실제 회원 ID로 보호된 액션을 실행합니다. 주문·주소 등 기존 쇼핑몰 fixture 읽기는 아직 실제 DB로 전환하지 않았습니다. 실제 회원의 변경 사항이 fixture 화면에 반영되지 않거나 fixture 주문의 소유권 검사가 실패할 수 있습니다. 실계정으로 쇼핑몰 전체 기능을 제공하기 전에는 해당 도메인의 저장·조회 전환이 필요합니다.
- 배포 환경에서 회원가입을 차단하는 기능은 이번 변경에 포함하지 않았습니다.

## 로컬 검증

```sh
node --test tests/*.test.mjs
npm run typecheck
npm run lint
npm run build
```

일반 테스트 실행에서는 DB 테스트 4개를 건너뜁니다. DB 테스트는 `bang-signup-test-*` 이름의 별도 임시 Docker 컨테이너만 허용하며 실제 Supabase에 연결하지 않습니다.

```sh
SIGNUP_TEST_CONTAINER=bang-signup-test-20261011 node --test tests/signup-db.test.mjs
```

DB 테스트는 매번 별도 테스트 DB를 생성해 회원·동의 저장 실패 시 전체 롤백, 메타데이터·약관 검증, 확인 시각 동기화, RLS, 마이그레이션 사전 검사, 롤백 후 데이터 보존을 확인합니다.

## 복구

문제가 있으면 앱 코드도 이전 버전으로 되돌리고, 별도 승인 후 `rollback/20261011000000_atomic_signup.sql`을 실행합니다. 복구 SQL은 이번에 만든 트리거 두 개와 함수 두 개만 제거하며 생성된 회원·동의 데이터는 보존합니다. Auth 계정이나 회원 데이터를 삭제하지 않습니다.
