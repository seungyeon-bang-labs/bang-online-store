# Supabase DB 적용·검증 기록

이 문서는 회원가입과 상품 카탈로그의 DB 적용·검증 이력을 관리합니다. 날짜가 있는 검증 결과는 해당 작업 당시를 기준으로 합니다.

## 현재 상태와 적용 조건

- 회원 인증은 Supabase Auth를 사용하고, 회원·약관·상품·카테고리는 실제 DB에서 조회합니다. 상품·카테고리 이미지는 Storage에서 제공합니다.
- 기존 주문·리뷰·문의·혜택 등 데모 내역은 fixture를 유지합니다. 현재 카탈로그 판매량·적용 할인·SALE 캠페인과 홈 직접 구성 섹션은 DB에서 조회합니다. 이벤트 배너의 기존 출처와 NEW 분류 기준은 유지합니다.
- 현재 앱은 `AUTH_FEATURES_ENABLED`가 정확히 `true`일 때 회원가입·이메일 인증·비밀번호 찾기를 허용합니다. 제한 모드에서도 로그인·로그아웃은 사용할 수 있습니다.
- 아래 SQL은 기존 회원·약관 스키마 등을 전제로 작성한 변경 이력입니다. 빈 Supabase 프로젝트 전체를 초기화하는 스크립트가 아니므로, 새 환경에서는 기존 스키마와 각 사전점검 조건을 먼저 준비해야 합니다.
- 기존 SQL은 SQL Editor에서 적용했으며 CLI 마이그레이션 이력에는 등록하지 않았습니다. 이미 적용된 SQL을 재실행하거나 이력 정리 없이 `supabase db push`를 실행하지 않습니다.
- 상품 집계·할인·홈 진열의 스키마와 초기 72건은 실제 DB에 적용하고 공개 조회까지 검증했습니다. 상품 Service·Model과 카드·상세·장바구니·필터·SALE의 DB 할인 연결, 최종 검증과 README 갱신을 마쳤습니다. 판매량은 고정 데모 값이며 자동 집계하지 않습니다.

앱 실행과 환경변수 설정은 [프로젝트 README](../README.md)를 참고합니다.

스키마 SQL과 seed SQL은 각각 별도의 트랜잭션입니다. seed 검사나 마지막 등록이 실패하면 이번 seed 등록 전체가 롤백되지만 이미 생성한 스키마는 남습니다. 초기 대상 행이 하나라도 있으면 덮어쓰기·건너뛰기·자동 보충 없이 중단합니다. 같은 상품에 연결된 활성 캠페인의 기간 중복은 과거·예정 기간도 검사하고, `[starts_at, ends_at)`의 인접 기간은 허용합니다. 소수 할인율은 정수 형 변환 전에 거부합니다.

다섯 테이블 모두 RLS를 사용합니다. 활성 상품 집계, 진행 중인 활성 할인과 활성 상품 연결, 활성 홈 섹션과 활성 상품 연결을 anon·authenticated에 공개하고 직접 쓰기는 차단합니다. 데모 판매량 수치도 공개 API로 조회되며 실제 주문 집계로 전환하기 전 공개 범위를 다시 검토해야 합니다. RLS가 오류 없이 행을 숨기는 경우가 있으므로 실제 적용 후에는 전체 등록 결과와 익명 API의 예상 ID·값·연결을 대조해야 합니다.

```sh

node --test tests/merchandising-rules.test.mjs
```

신규 DB 검증 15개와 기존 카탈로그 검증 23개가 통과했습니다. 새 순수 규칙·가격 UI 테스트 6개는 UTC와 America/New_York에서도 통과했고 타입 검사·린트도 통과했습니다. 검증에는 72건 원본 대조, 추가 상품이 있는 카탈로그, 기존 대상 충돌, 원본 소수 할인율 거부, 과거·예정·비활성·인접 기간, 마지막 등록 실패 시 전체 롤백과 고정 기간 재시도, 역할별 공개 조회·쓰기 차단과 읽기 전용 사전 확인을 포함합니다.

실제 관리자 조회로 72건의 전체 입력값·키·연결을 원본과 대조했습니다. 2026-10-19 18:36 KST 검증 시 상품 27개가 모두 활성이고 캠페인 3개가 진행 중이므로, 실제 anon 클라이언트에서도 27/3/15/2/25건이 공개되는지 exact count와 전체 필드 대조로 확인했습니다. 할인 연결 15건의 캠페인 FK 포함 조회도 일치했습니다. 다섯 테이블의 RLS와 SELECT 정책, anon·authenticated의 SELECT 허용 및 INSERT·UPDATE·DELETE·TRUNCATE 권한 부재, 새 갱신 트리거 3개를 확인했습니다. 기존 상품 27건·상품 갱신 트리거·`complete_signup` 함수는 유지되어 있습니다. 실제 값을 변경하는 음성 테스트는 실행하지 않았습니다.

앱 DB 조회 연결의 진행 상태는 아래 Repository 전환 기록으로 구분합니다. 데이터가 등록된 현재 상태에서 빈 상태 전용 복구 SQL은 실행을 거부하며 자동으로 데이터나 다른 객체를 삭제하지 않습니다. 기존 수동 적용 이력을 그대로 두고 CLI 이력을 임의 등록하지 않았습니다.

### 실제 프로젝트 사전 확인 — 2026-10-19, 읽기 전용

Supabase 대시보드의 SQL Editor에서 `BEGIN TRANSACTION READ ONLY`로 사전 확인 항목을 조회했습니다. 여러 결과를 검토할 수 있도록 테이블·컬럼·타입·함수·트리거·제약·정책·권한·역할·상품 참조와 CLI 이력 테이블 존재 여부를 하나의 JSON 결과로 모았습니다. 스키마·데이터·권한은 변경하지 않았습니다.

- 대상은 `plamqblmcavrtioajopz`의 `postgres` DB이며 PostgreSQL 17.6입니다.
- 상품은 27건이고 초기 등록에서 참조하는 ID 1~27이 모두 존재하며 `active`입니다.
- `products.id`는 bigint PK이고 RLS가 활성화되어 있습니다. `products_active_read`는 anon·authenticated에 활성 상품 SELECT만 허용하며 두 역할은 superuser·BYPASSRLS가 아닙니다.
- 신규 테이블 5개와 같은 이름의 타입은 없으며 `private.set_merchandising_updated_at`도 없습니다. 기존 상품 객체의 표시·FK·제약·`products_updated_at` 트리거와 `private.set_catalog_updated_at` 함수는 유지되어 있습니다.
- `supabase_migrations.schema_migrations` 테이블이 없습니다. 기존 수동 적용 기록과 일치하므로 전체 `supabase db push`를 실행하지 않습니다.

위 사전 확인은 실제 적용 전 상태의 기록입니다. 이후 사용자 승인에 따라 스키마·초기 72건을 적용하고 관리자·익명 조회 검증을 완료했습니다. 타입 갱신과 앱 DB 연결의 완료 여부는 각각 구분해 기록합니다.

## Repository DB 조회 전환 — 2026-10-19

구현 계획 5단계에서 상품 집계·할인 후보·홈 직접 구성 섹션의 서버 전용 Repository를 실제 공개 DB 조회로 전환했습니다. 기존 공개 서버 클라이언트의 `cache: 'no-store'`를 유지하며 관리자 키나 새 환경변수를 추가하지 않았습니다. 기존 데모 상품·주문 등의 fixture 경로는 유지했습니다. 이후 상품 Service·Model 주입은 아래 6단계 기록을 따르며 SALE 페이지의 캠페인 구성은 7단계 작업입니다.

- 상품은 `stats:product_stats(...)` 선택적 1:1 관계를 읽습니다. 집계가 없는 상품의 null과 품절 옵션을 유지하고 기존 활성·상품 ID·카테고리·스타일 필터와 공개 이미지 URL 조립을 보존했습니다.
- 할인은 상품 ID 묶음으로 `discount_items`를 읽으며 단일 부모 `discounts!inner`의 메타데이터를 같은 응답으로 받습니다. 사용처가 없는 기존 fixture 조회 메서드 대신 `findByProductIds`를 제공합니다.
- 직접 구성 섹션은 활성 부모와 연결 항목을 각각 조회해 기존 반환형을 유지합니다. 섹션은 표시 순서·ID, 연결 항목은 섹션 ID·표시 순서·상품 ID로 정렬합니다. 부모가 없으면 연결 항목 요청을 생략합니다.

실제 Data API 설정의 Max Rows는 **1,000행**임을 읽기 전용으로 확인했습니다. 당시 상품·집계·캠페인·할인 연결·섹션·진열 연결은 27/27/3/15/2/25건이고, 상품당 옵션·이미지·할인 연결의 최대는 5/2/1개, 섹션당 연결은 최대 15개입니다. 옵션은 기존 사이즈 CHECK와 `(product_id, size)` 고유 제약으로 최대 9개이므로 중첩 조회를 유지합니다. 이미지는 개수 제한이 없어 최상위 별도 조회로 분리했습니다.

상품·이미지·할인·섹션·연결 조회는 페이지당 500행 이하, ID 필터는 묶음당 100개 이하로 나눕니다. 정확한 전체 행 수와 실제 반환 길이로 계속 조회하므로 더 작은 상한을 흉내 낸 HTTP 응답에서도 연결을 모두 수집합니다. 고유 키를 포함한 정렬을 유지하며 중간 실패·누락된 페이지·집계용 응답 메타데이터 누락을 부분 성공으로 반환하지 않습니다. 여러 페이지 전체의 원자적 스냅샷을 보장하지 않는 기존 설계는 유지합니다.

새 Repository 테스트 10개와 기존 카탈로그 테스트는 실제 SDK의 HTTP 경계에 가짜 URL·키·응답을 사용합니다. DB 판매량 사용, stats null, 다중 페이지·ID 묶음과 이미지 소유권, 중간 실패, 필수 관계 누락, 실제 공유 클라이언트의 no-store와 다음 조회의 변경값 반영을 확인했습니다. 별도의 실제 anon 읽기 검증에서도 상품 27개·집계 27개·이미지 30개·할인 후보 15개·섹션 2개·진열 연결 25개와 원본 값의 일치를 확인했습니다. 이 검증으로 원격 데이터를 변경하지 않았습니다.

최종 전체 Node 테스트는 **193개 통과·실패 0개·기존 회원가입 DB 테스트 4개 skip**입니다. 전용 회원가입 컨테이너 미설정으로 건너뛴 결과이며 카탈로그·신규 집계 SQL 검증은 승인된 격리 컨테이너에서 실행했습니다. 타입 검사와 린트·diff 공백 검사도 통과했습니다.

## 상품 Service·Model 할인 연결 — 2026-10-19

구현 계획 6단계에서 실제 상품 Service에 할인 Repository를 필수로 주입했습니다. 상품을 읽기 전에 기준 시각을 한 번 확보하고, 활성 상품 ID를 묶어 받은 후보로 `discountRate`와 `appliedDiscountId`를 함께 결정합니다. 후보가 없는 정상 결과는 0/null이고 후보 조회 실패는 오류로 전파합니다. 상품이 없으면 할인 요청을 생략합니다.

상품 Mapper는 결정값을 두 번째 필수 인자로 받아 Model을 만들고, 카드·상세·장바구니·가격 필터·할인율 정렬·홈 할인 상품 선정은 Model 필드를 사용합니다. 상품 ID로 전역 fixture 할인을 다시 찾던 함수를 제거했습니다. 홈은 상품 조회와 신규 상품 선정에 같은 now를 전달하며, 상세 본문의 상품·다른 색상 조회와 장바구니의 상품·스타일 조회도 각각 한 기준 시각을 공유합니다.
