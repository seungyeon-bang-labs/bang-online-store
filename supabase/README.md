# Supabase DB 적용·검증 기록

이 문서는 회원가입·상품 카탈로그·장바구니의 DB 적용·검증 이력을 관리합니다. 날짜가 있는 검증 결과는 해당 작업 당시를 기준으로 합니다.

## 현재 상태와 적용 조건

- 회원 인증은 Supabase Auth를 사용하고, 회원·약관·상품·카테고리는 실제 DB에서 조회합니다. 상품·카테고리 이미지는 Storage에서 제공합니다.
- 기존 주문·리뷰·문의·혜택 등 데모 내역은 fixture를 유지합니다. 현재 카탈로그 판매량·적용 할인·SALE 캠페인과 홈 직접 구성 섹션은 DB에서 조회합니다. 이벤트 배너의 기존 출처와 NEW 분류 기준은 유지합니다.
- 현재 앱은 `AUTH_FEATURES_ENABLED`가 정확히 `true`일 때 회원가입·이메일 인증·비밀번호 찾기를 허용합니다. 제한 모드에서도 로그인·로그아웃은 사용할 수 있습니다.
- 아래 SQL은 기존 회원·약관 스키마 등을 전제로 작성한 변경 이력입니다. 빈 Supabase 프로젝트 전체를 초기화하는 스크립트가 아니므로, 새 환경에서는 기존 스키마와 각 사전점검 조건을 먼저 준비해야 합니다.
- 기존 SQL은 SQL Editor에서 적용했으며 CLI 마이그레이션 이력에는 등록하지 않았습니다. 이미 적용된 SQL을 재실행하거나 이력 정리 없이 `supabase db push`를 실행하지 않습니다.
- 상품 집계·할인·홈 진열의 스키마와 초기 72건은 실제 DB에 적용하고 공개 조회까지 검증했습니다. 상품 Service·Model과 카드·상세·장바구니·필터·SALE의 DB 할인 연결, 최종 검증과 README 갱신을 마쳤습니다. 판매량은 고정 데모 값이며 자동 집계하지 않습니다.

앱 실행과 환경변수 설정은 [프로젝트 README](../README.md)를 참고합니다.

## 장바구니 Gate A 적용·검증 — 2026-10-23

사용자가 대상·단일 SQL·권한 변경·생성 타입의 로컬 반영을 승인한 뒤 **BANG Online Store** 프로젝트 `plamqblmcavrtioajopz`의 `main / PRODUCTION`에 적용했습니다. 앱 URL·CLI 프로젝트 목록·대시보드의 대상을 대조했고 SQL Editor의 `postgres` 역할로 아래 migration 한 개만 실행했습니다. 전체 `supabase db push`·기존 SQL 재실행·seed·처리 이력 등록은 하지 않았습니다. CLI 이력 테이블은 없으며, 이전 SQL과 동일하게 SQL Editor 적용 기록으로 관리합니다.

- 사전 점검: [cart-preflight.sql](./checks/cart-preflight.sql)
- 적용 SQL: [20261023000000_cart.sql](./migrations/20261023000000_cart.sql)
- 빈 상태 전용 복구: [rollback SQL](./rollback/20261023000000_cart.sql)
- 적용 SQL SHA-256: `17005727b93a4c0e4d9642a21b930f9b9f7134a3554757053a700b4e72be7bc1`

`carts`, `cart_items`, `cart_operations` 세 테이블과 공개 RPC `get_cart`, `apply_cart_operation`, private 함수 9개, 갱신 트리거 2개, 본인 SELECT 정책 3개를 생성했습니다. 일반 사용자의 직접 쓰기를 차단하고 authenticated의 본인 조회와 공개 RPC 실행을 허용합니다. 두 RPC는 `auth.uid()`·예상 계정·실제 Auth 이메일 인증·활성 회원·미삭제 상태를 검증하고, 회원 장바구니 잠금 아래 변경과 이력을 한 트랜잭션으로 처리합니다. 재고를 예약·차감하지 않습니다.

이후 `apply_cart_operation`의 입력 검증·정규화(`cart_normalize_operation`)나 서버 `cartCommandSchema`를 바꿀 때는 기존 v1 요청과 하위 호환을 유지해야 합니다. 브라우저에 남은 미완료 요청은 같은 요청 ID로 다시 전송되며, 이미 반영된 요청이 새 규칙에서 invalid·conflict로 바뀌면 클라이언트가 확정 거부로 처리합니다.

실제 PostgreSQL 17.6에서 READ ONLY 사전 점검을 수행해 필수 타입·기존 RLS·회원 조회 정책·역할·실행 권한을 확인했고, 인증 미러의 불일치는 0건이었습니다. 적용 직전 신규 테이블·타입·함수 이름 충돌이 없고 기존 `complete_signup` 정의 해시가 같은 것을 다시 확인했습니다. migration 실행 결과는 `Success. No rows returned`였습니다.

적용 후 실제 DB의 읽기 전용 검사 12개가 모두 통과했습니다.

| 항목 | 확인 결과 |
| --- | --- |
| 테이블 | 3개 모두 postgres 소유·RLS 활성·migration 마커 일치 |
| 조회·직접 쓰기 | authenticated SELECT 허용, anon SELECT 차단, anon/authenticated의 직접 DML·TRUNCATE·REFERENCES·TRIGGER 권한 차단 |
| 함수 | 11개 모두 소유자·반환 타입·고정 search_path·마커 일치; 공개 2개만 SECURITY DEFINER |
| 함수 실행 | 공개 RPC는 authenticated만 실행 가능, 일반 역할과 service_role의 private 함수 직접 실행 권한 없음 |
| 정책·참조·트리거 | SELECT 정책 3개, FK 4개와 삭제 동작, 갱신 트리거 2개 정상 |
| 정렬 | `cart_items(cart_id, created_at, id)` 인덱스 존재 |
| 데이터 | carts·cart_items·cart_operations 모두 0건 |
| 기존 회원가입 RPC | 적용 전후 `complete_signup` 정의 MD5 `f4979d952e70f7c945b67ac47e2f2d79` 일치 |

추가 카탈로그 조회로 제약 14개(PK 3·UNIQUE 2·FK 4·CHECK 5)와 NOT NULL 컬럼 17개를 확인했습니다. 기존 회원·Auth·카탈로그 행이나 정책을 변경하는 SQL은 실행하지 않았습니다. 실제 회원 RPC·장바구니 쓰기도 호출하지 않았습니다.

같은 project ref의 public 스키마에서 설치된 Supabase CLI로 타입 후보를 생성해 [공유 타입](../src/shared/types/supabase.ts)에 반영했습니다. 후보에서 새 테이블 3개·RPC 2개를 제외하면 모든 기존 타입이 동일함을 AST로 대조했고 `Functions.complete_signup`과 기존 FK를 보존했습니다. RPC 응답의 revision은 별도의 문자열 DTO 계약을 유지합니다. 반영 후 타입 검사·린트·공백 검사가 통과했습니다.

이 SQL의 격리 DB 검증 30개와 로컬 저장 테스트 15개는 실제 적용 전에 모두 통과했습니다. 마지막 전체 검증은 265개 중 234개 통과·실패 0개·기존 다른 DB 테스트 31개 skip이며, 생성 타입 반영 뒤 전체 DB 테스트를 불필요하게 반복하지 않았습니다. 이번 실제 검증은 스키마·권한·빈 상태·타입 일치 확인이며 회원·다중 탭 브라우저 검증은 아닙니다.

아래 Gate A 당시에는 앱 UI 연결이 후속 작업이었으며, 현재 연결 구현과 로컬 검증은 다음 통합 검증 기록에 정리했습니다. 초기 `get_cart`도 빈 carts 행을 만들 수 있으므로 실제 회원 브라우저/쓰기 검증은 Gate B의 별도 승인 뒤에 수행합니다. rollback은 세 테이블이 모두 비어 있고 마커가 일치할 때만 신규 객체를 제거하며, 행·이력이 생긴 뒤에는 거부합니다. 자동 데이터 삭제·CASCADE 복구는 하지 않으며 rollback 자체도 별도 승인 대상입니다.

## 장바구니 앱 연결·통합 검증 — 2026-10-23

회원 장바구니는 Route Handler(`/api/cart/*`)의 실제 세션 확인 → Service → 세션별 RPC Repository를 통해 조회·변경합니다(2026-10-24 Server Action에서 전환, DB·RPC 변경 없음). guest 항목과 계정별 고정 요청 큐는 localStorage, 화면 캐시와 UUID 선택은 Provider별 Zustand 메모리에 둡니다. 앱 코드에 관리자 키나 직접 테이블 쓰기를 추가하지 않았습니다. 초기 get_cart도 쓰기일 수 있으므로 아래 로컬 구현 검증과 실제 회원 실행을 구분합니다.

| 검증 | 결과 |

| 전체 Node 테스트 | 366개 중 305 통과, 실패0, skip61 (cart DB30 + 기존 다른 DB31) |
| 격리 cart DB 별도 실행 | 30/30 통과, 실패0·skip0 |

격리 cart DB는 네트워크·호스트 포트가 없는 소유 컨테이너만 사용했고 임시 DB0개를 확인한 뒤 중지했습니다. 다음 명령으로 해당 환경에서 검증합니다. 다른 DB용 skip은 통과로 세지 않습니다.

```sh

```

최종 독립 리뷰에서 발견한 탭 간 인증 완료 전파, 응답 유실 후 상품 담기 선택 정리, 비회원 상품·자체 옵션 정보 불일치는 실패 회귀 테스트를 먼저 확인한 뒤 수정했습니다. 재시도는 동일 요청 ID를 유지하며, 다른 탭이 큐를 먼저 처리해도 원래 화면이 해당 요청의 확정 결과를 확인합니다. 비회원 응답의 자체 옵션이 없거나 재고·사이즈·추가금이 모순되면 로컬 정리를 저장하지 않고 재시도를 표시합니다. 인증 진행 중에는 이전 회원 화면을 다시 열지 않습니다.

비회원 프로덕션 브라우저에서 별도 로컬 출처의 상품1 M·XL 묶음 담기, 새로고침 복원, 장바구니 전체 미선택, M→기존 XL 병합 시 대상 UUID·수량2·선택 이관을 확인했습니다. 추가로 두 탭의 수량·배지 동기화, 상품 조회 차단 시 원본 보존·잠금·재시도 복구, 선택 항목만 삭제, 주문 준비 안내를 확인했습니다. 390×844 모바일 화면의 선택 합계와 가로 넘침 없음도 확인했습니다. 품절 보존은 검증 전용 localStorage에 실제 카탈로그의 stock0 옵션5·수량2를 구성해 수량 유지·전체 선택 제외·수량 버튼 잠금·개별 삭제를 확인했으며 원격 재고를 바꾸지 않았습니다. 검증용 항목은 UI로 모두 정리했습니다. 기존 :3000 개발 서버도 유지한 채 별도 출처에서 비회원 담기·새로고침·진입 후 수량1과 전체 미선택을 확인하고 테스트 항목을 정리했습니다. 회원 쿠키 없이 실행했으며 이 결과는 회원 StrictMode 병합 검증이 아닙니다.

사용자의 명시적 승인 후 기존 공개 데모 계정 demo@example.com만 사용했습니다. 대상은 상품1의 M(옵션2)·XL(옵션4), 각 수량1–3 범위였으며 계정 생성·회원 설정·카탈로그·재고·권한·스키마를 변경하지 않았습니다. 기존 장바구니 ID는 검증 전후 동일합니다.

최종 처리 이력은 merge_guest2·add_items1·adjust_quantity4·change_option2·remove_items2입니다. 초기 병합과 개발 초기 병합이 각1건이고 응답 유실 재시도·재로그인·새로고침이 별도 중복 변경을 만들지 않았습니다. 일회성 브라우저 fetch 대체와 요청 차단은 원복했으며 승인된 테스트 항목만 UI로 정리했습니다. SQL Editor는 SELECT만 실행했고 쿼리 저장·CSV 내보내기·이력 삭제는 하지 않았습니다.

항목의 빈 상태만 복구했으며 revision·처리 이력·수정 시각은 남습니다. 데이터·이력이 존재하므로 빈 테이블 전용 rollback을 실행하지 않습니다.

### 추가 승인된 실제 A/B 전환 검증 — 2026-10-24

사용자가 지정한 기존 B 계정의 활성·회원/Auth 이메일 인증과 장바구니 행·항목·이력 없음 상태를 SELECT로 확인했다. B의 첫 장바구니 생성과 상품1 XL(옵션4)1개 담기·삭제, A의 상품1 M(옵션2)1개 담기·삭제 및 응답 지연·같은 요청 복구를 별도로 승인받았다. B 비밀번호는 사용자가 브라우저에서 직접 입력했으며 채팅·문서·검증 로그로 수집하지 않았다.

- 이메일·비밀번호 가입과 이메일 OTP 인증을 대상으로 합니다. OTP는 앱 기준 6자리·300초입니다. Supabase Auth 설정도 같은 값이어야 합니다.
- 트리거는 모든 `auth.users` INSERT에 적용됩니다. 관리자 생성·초대·OAuth 등도 이름, 휴대폰, 약관 ID 메타데이터가 없으면 실패합니다. 다른 가입 경로를 추가할 때 함께 설계해야 합니다.
- 약관 버전 ID는 내용과 요구 조건이 바뀌면 새 ID로 발행해야 합니다. 현재 약관 목록과 화면의 목록이 달라지면 페이지를 새로고침하고 다시 동의해야 합니다.
- 확인된 실제 회원 ID로 보호된 액션을 실행합니다. 주문·주소 등 기존 쇼핑몰 fixture 읽기는 아직 실제 DB로 전환하지 않았습니다. 실제 회원의 변경 사항이 fixture 화면에 반영되지 않거나 fixture 주문의 소유권 검사가 실패할 수 있습니다. 실계정으로 쇼핑몰 전체 기능을 제공하기 전에는 해당 도메인의 저장·조회 전환이 필요합니다.
- 2026-10-11 SQL 변경에는 배포 데모의 회원가입 차단 기능을 포함하지 않았습니다. 현재 앱의 인증 기능 제한은 별도로 구현한 `AUTH_FEATURES_ENABLED`로 제어합니다.
